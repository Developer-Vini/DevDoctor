# DEVDOCTOR — PROMPT DE DESENVOLVIMENTO

Você é um engenheiro de software sênior especializado em Node.js, TypeScript, CLI tools, análise estática de código, segurança de aplicações e arquitetura de software.

Sua tarefa é construir uma aplicação open source chamada **DevDoctor**.

O DevDoctor será uma CLI capaz de analisar um projeto de software local, encontrar problemas de qualidade, segurança, configuração, Git, documentação e dependências, atribuir uma pontuação ao projeto e, quando for seguro, corrigir automaticamente alguns problemas.

O projeto deve ser **realmente funcional**, não um mockup, demonstração ou protótipo.

---

# 1. OBJETIVO

O usuário deverá conseguir executar:

```bash
dev-doctor
```

dentro de qualquer projeto suportado.

O DevDoctor deverá:

1. Detectar automaticamente o tipo do projeto.
2. Construir um contexto sobre o projeto.
3. Executar verificações independentes.
4. Detectar problemas.
5. Classificar os problemas por severidade.
6. Calcular uma pontuação geral.
7. Mostrar um relatório bonito no terminal.
8. Permitir saída em JSON.
9. Permitir saída em Markdown.
10. Corrigir automaticamente problemas considerados seguros.
11. Funcionar sem qualquer serviço de IA.
12. Ser modular para permitir novos checks no futuro.
13. Possuir testes automatizados.
14. Ser preparado para publicação no npm.
15. Ser preparado para execução em CI/CD.

---

# 2. REGRA FUNDAMENTAL

NÃO use IA como parte obrigatória do núcleo.

O DevDoctor deve funcionar 100% offline para todas as análises determinísticas.

A arquitetura deve permitir adicionar IA futuramente como uma camada opcional.

A IA futura deverá servir principalmente para:

* explicar problemas;
* sugerir soluções;
* auxiliar em correções complexas;
* interpretar problemas difíceis.

A IA NÃO deve ser necessária para:

* detectar `.env`;
* detectar arquivos perigosos;
* analisar Git;
* analisar package.json;
* verificar dependências;
* procurar secrets;
* verificar documentação;
* calcular score;
* executar checks determinísticos.

# 6. CONCEITO DE CHECK

Todos os diagnósticos deverão ser implementados como checks independentes.

Crie uma interface semelhante a:

```ts
interface Check {
    id: string;
    name: string;
    description: string;
    category: CheckCategory;

    run(context: ProjectContext): Promise<CheckResult>;
}
```

O resultado deverá conter informações como:

```ts
interface CheckResult {
    id: string;
    name: string;
    category: CheckCategory;
    status: "pass" | "warning" | "error";
    severity: "info" | "low" | "medium" | "high" | "critical";
    message: string;
    details?: string;
    file?: string;
    line?: number;
    fixable: boolean;
    scoreImpact: number;
}
```

Os checks devem ser registrados em um registry central.

O core não deve conhecer detalhes internos de cada check.

# 9. CHECKS INICIAIS

Implemente pelo menos os seguintes checks.

## SECURITY

### security.env

Verifique:

* `.env`
* `.env.local`
* `.env.production`
* `.env.development`

Verifique se arquivos sensíveis estão sendo rastreados pelo Git.

Resultado exemplo:

```text
❌ .env is tracked by Git
```

---

## security.secrets

Procure possíveis secrets.

Detecte padrões como:

```text
API_KEY=
SECRET=
PASSWORD=
TOKEN=
PRIVATE_KEY=
ACCESS_KEY=
CLIENT_SECRET=
```

Também procure valores hardcoded suspeitos.

Evite gerar falsos positivos óbvios.

Nunca exiba o valor completo de um secret encontrado.

Exiba algo como:

```text
Possible secret detected

File:
src/config.ts

Line:
18

Value:
sk_************91
```

Nunca coloque secrets no relatório JSON ou Markdown em texto puro.

* `.env` rastreado;

# 18. FIX SYSTEM

Crie um sistema separado para correções.

Nunca altere arquivos automaticamente sem uma regra explícita de segurança.

Exemplos de correções seguras:

```text
Criar .gitignore
Adicionar .env ao .gitignore
Criar .env.example
Criar README básico
```

Antes de alterar um arquivo, faça backup ou ofereça:

```bash
dev-doctor fix --dry-run
```

O `--dry-run` deve mostrar:

```text
Would modify:

.gitignore
package.json

No files were changed.
```

Também permita:

```bash
dev-doctor fix --check security.env
```

# 20. CI/CD

```bash

```

* não use animações;

* produza output legível;
* retorne exit codes apropriados.

Exemplo:

```text

1 = problemas encontrados
2 = erro interno
```

```bash

```

```text
CI FAILED

Score: 74
Required: 80
```

# 36. PRINCÍPIO FINAL

O DevDoctor deve parecer uma ferramenta que um desenvolvedor realmente instalaria e utilizaria no dia a dia.

Priorize:

**confiabilidade > quantidade de funcionalidades**

**simplicidade > complexidade**

**detecção real > demonstração**

**segurança > automação agressiva**

**arquitetura extensível > código rápido e descartável**

Não transforme o projeto em um chatbot.

O diferencial do DevDoctor deve ser:

> **“Run one command. Know the health of your project.”**

Comece pela FASE 1, implemente completamente, execute os testes e mostre a estrutura e os arquivos criados antes de avançar para a FASE 2.
